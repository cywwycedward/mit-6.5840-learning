MapReduce 为什么能重试任务

worker 没有按时完成任务时，coordinator 可以把同一逻辑任务再交给别人。但“再跑一次”不是魔法：要保持结果有意义，应用的 Map/Reduce 必须满足明确的确定性边界。这一节只解释这条故障语义。

对应 MIT 6.5840：L1：Introduction。L1 以 MapReduce 说明分布式系统的 partial failure（部分失败）与容错：framework 跟踪 task、调度 worker 并从 crash 中恢复。本节忠实解释它的重试动机与正确性前提，不提供 Lab 1 的实现方案。

单一技能解释一次重试为何仍能保持作业语义
完成标准区分超时、crash、straggler 与完成
暂不做的事不设计 RPC、timer 或状态代码

资料边界。“任务重试”同时出现在 L1 讲义、原始 MapReduce 论文和 Lab 1 中，但细节不同：论文讨论 Google 集群中的 master、worker ping、local disk 与 atomic commit；2026 Lab 使用 coordinator，并规定 10 秒后重分配未完成 task。下面会明确标记概念与 Lab 专有规则，避免把其中一个环境的实现细节当作另一个的要求。

0. 一分钟回忆：重复执行时，哪个结果是“同一个任务”的结果？

上一节中，一个 Map task 为输入 split 产生 intermediate key/value pairs。现在假设 coordinator 把同一个 split 的 Map task 发给 A，A 沉默后又发给 B。若 A 与 B 产生的内容不同，shuffle 还能得到一个清晰的词频结果吗？

检查 0

对于同一份输入，重试后的 Map 输出应满足什么条件？

1. coordinator 管逻辑任务，不保证知道机器真相

原论文中的 master（本课程 Lab 改称 coordinator）为每个 Map 和 Reduce task 记录状态。一个有用的心智模型是：

逻辑 task 状态coordinator 知道什么下一步可能做什么
idle还没有有效执行者分配给空闲 worker
in-progress已分配，但尚未记录为完成等待；若认为执行不再可靠则重新分配
completed已接受该逻辑 task 的有效结果把结果位置提供给下一阶段，或继续其他 task

这不是在猜测“worker 此刻一定已 crash”。分布式系统常见的难点是：coordinator 看到的是没有收到完成消息，而不是机器内部的真相。它可能 crash、卡住、网络断开，或只是很慢。

Lab 专有规则。2026 Lab 1 要求：若 worker 在合理时间内未完成，coordinator 等待 10 秒 后将同一 task 给另一 worker。这个 timeout 是作出重试决策的规则，不是“已经证明原 worker 死亡”的证据；L1 讲义和论文提供的是更一般的部分失败背景。

2. 重试安全的前提：deterministic

deterministic（确定性）表示：给定相同输入，函数产生相同输出。L1 的 MapReduce 讨论要求 Map 和 Reduce 应是 pure deterministic functions（纯确定函数）：它们只依赖自己的参数或输入，不偷偷读取会变化的外部状态，也不以随机结果或外部副作用改变语义。

同一 input split │ ├─► Map execution A ─► intermediate output X │ └─► Map execution B（重试） ─► 也必须是 X coordinator 可以接受其中一次有效完成；Reduce 看见的仍是该逻辑 task 应有的数据。

词频的 Map 是典型例子：相同文本总会发出相同的 (word, 1) pairs；Reduce 对同一组 values 做加法也会得到相同计数。相反，若 Map 每次都附上当前时间或随机数，同一逻辑任务的重试可能改变 key/value，最终作业就取决于“哪次先被接受”，不再有清楚的顺序语义。

3. 不同的“没有按时完成”

情况含义本节应得出的结论
worker crash执行者确实停止，可能丢失其 local intermediate dataframework 需要让逻辑 task 有重新执行的路径
stragglerworker 很慢，但不一定失效慢不等于 crash；论文讨论 backup execution 来缩短尾部
超时coordinator 在期限内没观察到完成是重试依据，不是对 crash 的确定诊断
coordinator / master crash调度者自身停止不能假定它已容错；原论文实现中 master 失效会终止 job

论文还解释了为什么 Map 与 Reduce 的重跑边界可能不同：Map intermediate output 存在执行 Map 的 worker 的 local disk；那个 worker 失效时，已完成的 Map 也必须重新执行。Reduce 的最终输出存放在 global file system 时则不必重跑。这是论文的生产系统机制；Lab 的本机共享文件系统是教学化环境，不能直接照搬这些存储假设。

4. “完成”还需要安全地发布结果

原论文用 private temporary files（私有临时文件）生成任务结果，再以 atomic commit（原子提交）把某一次 Reduce 的结果发布为最终文件。这样两个 execution 即使重叠，读者也不会看到半写入的最终结果。这个机制配合 deterministic functions，才让分布式、有重试的执行对应一个清晰的无故障结果。

本节只建立语义，不要求实现。后面的 Go、RPC、文件与 coordinator 课程才会分别解释实现所需的工具和测试。此刻只要能说清：重试的是一个逻辑 task，而不是“同一 worker 的第二次机会”。
