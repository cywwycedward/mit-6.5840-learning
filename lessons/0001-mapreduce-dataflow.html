0. 先预测：重复词应该在哪里合并？

有两个输入分片：A = "rain sun rain"，B = "sun"。如果两台机器各自只看一个分片，它们能不能直接得出 rain 的全局次数？先选一个答案，再看理由。

检查 0

两次出现的 rain 都在 A 中，但 B 也会产生其他词。Map 完成后，哪个步骤负责把同一个词的值放到一起？

1. 应用写两个函数，框架承担分布式复杂度

L1 的核心观察不是“把一个循环拆到多台机器”，而是把职责分开：应用作者只描述数据如何转换；MapReduce framework（框架）负责把这些转换放到许多机器上执行，并处理分片、调度、通信和失败。

角色它提供或处理什么本节中的例子
应用定义 Map 与 Reduce 的业务含义词频统计：见到一个词就发出一次计数
MapReduce framework切分输入、调度 task、传递中间数据、并行与恢复让两个输入分片分别交给 worker，并把同词收集起来
worker执行被分配的一项 Map 或 Reduce task处理 A 或 B；稍后处理一个 key 的 values

术语卡：key/value pair。key 是用来归类的数据标签，例如词 rain；value 是随这个标签传递的信息，例如 1。写成 (rain, 1) 表示一对数据，而不是 Go 的语法，也不是 Go 的 map 类型。Map 输出的 pair 叫 intermediate（中间）key/value pair，因为它还不是最终结果。

概念上，两个应用函数的输入输出是：

Map(input record)              → zero or more intermediate (key, value) pairs
Reduce(intermediate key, values) → zero or more final output records

第二行的 values 是同一个 key 收集到的全部 values，不是只拿到其中一个值。上面的箭头是算法记号，不是需要编译的代码。

2. 一条完整的数据线：Map → shuffle → Reduce

设有两个 input split（输入分片），每个 split 对应一个 Map task。词频应用的 Map 对每个词发出 (word, 1)；Reduce 把同词的所有 1 相加。

Input split A: "rain sun rain" ─► Map A ─► (rain,1) (sun,1) (rain,1) Input split B: "sun" ─► Map B ─► (sun,1) │ ▼ shuffle / grouping rain ─► [1, 1] sun ─► [1, 1] │ ▼ Reduce(rain, [1,1]) ─► (rain,2) Reduce(sun, [1,1]) ─► (sun,2)

Map：每个 task 只需读取自己的输入，因此 Map A 与 Map B 可以并行。shuffle / grouping：框架按 intermediate key 重新组织来自所有 Map 的输出，使同一个 key 的 values 到同一个 Reduce。Reduce：对一个 key 及其 values 做真正的聚合，生成最终输出。

检查 1

Map A 发出 (rain,1)，Map B 也发出 (rain,1)。哪一种说法正确？

3. 分区不是聚合：它决定谁处理哪些 key

一个真实作业通常有 M 个 Map task 和 R 个 Reduce task。MapReduce 使用一致的 partition function（分区函数），例如 hash(key) mod R，把每个 key 分到一个 Reduce partition（Reduce 分区）。因此任意一个 key 的所有 values 都会到同一个 Reduce task；但一个 task 通常要处理多个不同 key。

这就是 L1 所说的 shuffle：Map 的 intermediate output 先按分区写出；每个 Reduce 获取所有 Map 在自己分区中的数据，再按 key 排序或分组，逐 key 调用 Reduce。作业成功时有 R 个输出文件，而不一定是一份单独的大文件。

不要混淆。“一个 Reduce task 处理一个 partition”不等于“一个 Reduce task 只处理一个 key”。分区是分工方式；grouping 才保证同 key 的 values 被放在一起。

4. 这条数据流带来的好处与限制

Map task 彼此不需要共享状态，Reduce task 也可在各自分区上并行，因此更多 worker 有机会提升吞吐量。L1 同时提醒：这不是自动的线性加速；网络、磁盘、CPU、内存和负载不均衡都可能成为瓶颈。

换来的限制是应用必须服从单一的批处理形状：Map → shuffle → Reduce。应用不能在 task 之间直接交互或保存跨阶段状态，只能通过 intermediate output 传递。这正是框架能接管大量分布式复杂度的原因。
