用 channel 交接任务，并让 worker 正确退出

一个 coordinator 把任务交给 worker 后，最危险的问题不是“暂时没任务”，而是“已经永远不会再有任务”。这一节只建立一个协议：发送方发送任务，并在任务流结束时关闭 channel；worker 用 range 接收并自然退出。

单一技能设计并追踪 channel 的任务结束协议
完成标准解释谁关闭、谁阻塞、何时退出
进入课程的意义为 coordinator / worker 的任务分发打基础

范围刻意很小。本节只讨论一条不带缓冲的整数任务流，以及它如何明确结束；缓存、取消、超时和其他高级变体都留到后面。这里使用的是独立小程序，不是真正的 Lab 代码。

首选主读：完成本节前后，阅读 Go 官方的 channel 类型、发送、接收 与 关闭章节；它们是本课所有阻塞和关闭结论的权威来源。

检查 0

Mutex 与 WaitGroup 分别解决什么问题？

复习入口：Mutex 速查、WaitGroup 速查。这节新增的 channel 负责第三件事：把一个值和“没有更多值”这两个事实交给另一个 goroutine。

1. 先画出协议，而不是先写 goroutine

本节的无缓冲 channel 是 Go 让 goroutine 交接有类型的值的通信对象；它让发送和接收在同一个交接点同步。把它想成任务的交接点，而不是一个可以随意读写的共享任务表。对于这节的一条任务流，先写清楚所有权：

角色它知道什么它可以做什么
producer（生产者）是否还会产生新任务发送任务；确认“再也没有”后宣布任务流结束
worker（消费者）当前收到的任务接收并处理任务；不负责宣布任务流结束

这个规则直接对应后端经验：一个请求队列的上游最清楚自己是否还能投递；下游只消费。MIT 的 coordinator/worker 模型也需要回答“任务由谁发出、何时不再发出、等待者怎样退出”，但本课使用的是独立小程序，不是实验解答。

2. 语法卡：创建、发送与接收

tasks := make(chan int)

tasks 是新变量名；:= 是第 1 节讲过的短变量声明；make 是本节第一次出现的内置函数；圆括号内的 chan int 指定它创建一个“元素类型为 int 的 channel”。chan 是 Go 关键字，int 限定这个 channel 只能交接整数。

这里没有写容量参数，所以它是无缓冲（unbuffered） channel：不能先把值塞进内部队列再继续。一次发送必须和一次接收配对，才能完成。Go 规范对 channel 类型 和 无缓冲发送的阻塞条件作了精确定义。

tasks <- 7：send（发送）

tasks 位于左边，是目标 channel；<- 的箭头朝向 channel；右边的 7 是要交接的整数。读成：“把 7 发送到 tasks”。若还没有 goroutine 正在接收，当前发送 goroutine 会在这一行等待。

task := <-tasks：receive（接收）

右侧的 <-tasks 从 channel 取一个值；箭头朝向左边的新变量 task。若还没有发送者，当前接收 goroutine 会阻塞。发送和与它配对的接收完成时，值才真正交接。Go 内存模型规定：一次发送先发生于对应接收的完成；也就是发送前在同一 goroutine 已完成的操作，能排在这次配对接收之前。这是受同步约束的交接，不只是“碰巧同时发生”。

3. API 卡：close(tasks) 不是一条任务

close(tasks) 调用内置函数 close；圆括号中是要关闭的 channel。它表达的是“以后不会再发送任何任务”，并不把某个特殊整数传给 worker。

本课的所有权规则是：唯一发送者在最后一次发送后关闭。关闭后再发送会 panic；再次关闭也会 panic。因此 worker 不该关闭它正在消费的 tasks，多个 worker 也不能各自猜测“任务结束了”。精确语义见 Go 规范的 close 与 send 章节。

for task := range tasks 的 for 和 range 已在第 1 节讲过；此处只补充它的 channel 边界：没有任务时它等接收；channel 已关闭且没有可接收任务时它结束循环。本课不用缓冲区，所以“关闭后还要先取走缓冲值”的变体留到以后。复习：for/range 速查。

检查 2

唯一 producer 已确认以后没有任何新任务。下一步最合适的动作是什么？

4. 把协议写成一个可测试的小程序

下面不是 MIT 实验代码，而是一条最小的任务流。worker 每收到一个任务就把 count 加一；它只能在 range 结束后才把计数发给 done，随后返回。

语法卡：go 加普通函数调用

go worker(tasks, done) 与第 1 节的 go func() { ... }() 使用同一个 go 关键字。这里 worker(tasks, done) 是一次普通函数调用：worker 是函数名，圆括号内的 tasks、done 是按顺序传入的参数；最前面的 go 让这次调用在新 goroutine 中执行。

没有“先运行谁”的承诺：执行 go 后，当前 goroutine 可以立刻继续，也可能是 worker 先继续。这里不依赖顺序：若 producer 先到 tasks <- 8，无缓冲 send 会等到 worker 到达 receive；若 worker 先到 receive，它会等发送。

// worker.go
package handoff

func worker(tasks chan int, done chan int) {
	count := 0
	for range tasks {
		count++
	}
	done <- count
}

函数参数的“名字在前、类型在后”与第 1 节相同：tasks chan int 和 done chan int 都是可发送也可接收整数的 channel。本节故意不使用单向 channel 类型，以免把“谁能关闭”与“谁能发送”的设计问题藏进类型语法里。

// worker_test.go
package handoff

import "testing"

func TestWorkerLeavesReceiveLoopAfterClose(t *testing.T) {
	tasks := make(chan int)
	done := make(chan int)

	go worker(tasks, done)

	tasks <- 8
	tasks <- 13
	close(tasks)

	if got, want := <-done, 2; got != want {
		t.Fatalf("count = %d, want %d", got, want)
	}
}
按发生顺序追踪这段测试
  1. 测试创建两个无缓冲 channel：tasks 交接工作，done 交回一个结果。
  2. go worker(tasks, done) 把一次普通函数调用放到新的 goroutine 中执行，但不保证它立刻先运行。若 producer 先执行第一条 send，它会等待，直到 worker 到达 range tasks 的接收点。
  3. 每个 tasks <- ... 都要和 worker 的一次接收配对。因此两个任务都已交接后，producer 才能调用 close(tasks)。
  4. worker 下一次尝试从 tasks 取任务时发现任务流已关闭，range 结束；它发送 count 到 done，然后返回。
  5. 测试在 <-done 等待结果。收到 2 后，已讲过的 if got, want := ... 检查两项任务是否都经过了 worker。

先预测，再改代码：若删除 close(tasks)，两个任务仍会被处理，但 worker 接着会在下一次 receive 上等待；它无法知道任务流已经结束，因此不会发送 done。测试也会等在 <-done。不要把这个故意卡住的版本当作一次长时间运行的命令；先用这条时序解释它为何没有退出路径。
