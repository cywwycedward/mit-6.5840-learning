# MIT 6.5840 学习工作区 Git 管理规范

## 1. 目的与适用范围

本规范让学习过程可回溯、可恢复，也让每一次代码或课程材料的变化都有清楚的原因。它服务于当前的个人学习工作区；目标是形成可靠的工程习惯，而不是模仿大型团队的重型流程。

截至 2026-08-17，工作区尚未初始化为 Git 仓库。因此本规范同时定义首次建库和之后的日常工作方式。

## 2. 仓库结构与跟踪边界

下表规定哪些内容是学习成果，哪些只是本机运行痕迹。

| 路径或内容 | 是否跟踪 | 原因与要求 |
| --- | --- | --- |
| `MISSION.md`、`NOTES.md`、`RESOURCES.md`、`AGENTS.md` | 必须 | 记录目标、教学偏好、可信来源和项目协作约定。 |
| `learning-records/`、`lessons/`、`reference/`、`assets/` | 必须 | 这些是可复习、可验证的课程成果及其共享组件。保留资料来源，不提交实验解答。 |
| `src/`、`go.mod`、`go.sum`、测试与示例 | 必须 | 这是可运行的练习或实验代码；依赖清单必须和代码一起提交。 |
| `.scratch/` 中的 `spec.md`、`issues/` 和 `map.md` | 必须 | 这是本仓库约定的本地问题跟踪记录，不因目录名含有 `scratch` 而忽略。 |
| `.codex/`、`.claude/` 中为本项目共享的技能或配置 | 默认跟踪 | 只有确认它们是可复现工作流的一部分时才提交；提交时说明来源与用途。密钥、缓存和机器专属设置不得提交。 |
| 可重建的二进制、覆盖率、profiling、日志、临时文件、密钥和本机 IDE 状态 | 禁止 | 由 [`.gitignore`](../.gitignore) 排除；如果一个文件可能含 token、cookie 或密码，先停止并确认再处理。 |

不以 `*.pdf`、`*.tar.gz` 这类宽泛规则忽略文件：现有课程资料就是仓库的一部分。新增第三方材料前，应确认来源、许可与是否适合保存副本；不能确认时保存官方链接和用途说明，而不是复制文件。

## 3. 分支模型

采用一个长期稳定分支和短生命周期工作分支：

```text
main  ─────●──────────●──────────  可复习、可运行的学习里程碑
            \        /
docs/git-workflow ────              一项聚焦的改动
```

- `main` 是唯一长期分支。每个提交都应是可理解的学习快照；有 Go 代码时必须通过约定的测试。
- 一项不止是错别字的改动，先从最新 `main` 创建工作分支。禁止在工作分支混入无关清理。
- 分支命名使用小写英文和连字符：`lesson/<topic>`、`exercise/<topic>`、`docs/<topic>`、`ref/<topic>`、`fix/<topic>`、`chore/<topic>`。例如 `exercise/safe-counter`。
- 完成后先自审，再以 fast-forward 合并回 `main`，随后删除工作分支。不要保留长期 `develop` 分支，也不需要 GitFlow。
- `main` 不允许 force-push；已经共享给远端的提交不改写历史。尚未共享的个人工作分支可以在合并前整理，但必须先确认没有他人基于它继续工作。

## 4. 提交规范

提交必须是原子的：一个提交只表达一个可用的理由。课程正文与其共享样式可同提交；某个练习的实现、测试和必要文档可同提交；不要把格式化全仓库、资料搬运和功能改动混在一起。

提交标题格式为：

```text
<type>(<scope>): <简短的动作说明>
```

`scope` 可省略；说明使用中文且不用句号。可用类型如下：

| 类型 | 适用场景 | 示例 |
| --- | --- | --- |
| `lesson` | 新增或修订可交互课程 | `lesson(git): 增加首次建库练习` |
| `ref` | 速查资料、课程来源或讲义索引 | `ref(git): 补充分支工作流速查表` |
| `docs` | 规范、目标、说明 | `docs(workflow): 定义 Git 管理规范` |
| `feat` | 新的练习/服务能力 | `feat(counter): 支持并发读取` |
| `fix` | 已观察到的错误修复 | `fix(counter): 保护 Value 的读取` |
| `test` | 只调整测试或测试工具 | `test(counter): 覆盖并发读取` |
| `chore` | 不改变学习内容或行为的维护 | `chore(repo): 初始化版本控制` |

如果对应 `.scratch/` 事项，在提交正文加一行 `Refs: .scratch/<feature>/issues/<NN>-<slug>.md`。若提交标志一个已验证的学习结论，更新相应 `learning-records/` 并在正文加一行 `Learning: <结论>`；不要把尚未验证的猜测写成学习记录。

## 5. 改动前、提交前与合并前

每次开始工作先看 `git status --short`：它只显示简洁状态，不会修改文件。若出现自己不认识的改动，先停下并确认来源，不要用重置或清理命令掩盖它。

提交前必须完成：

1. 检查 `git diff` 和 `git diff --cached`，确认没有密钥、生成物、无关格式化或实验解答。
2. 确认暂存区只包含本次目的的文件；使用 `git restore --staged <path>` 可以撤销暂存，且不会删除工作区文件。
3. 验证与改动相称：文档/HTML 逐个在浏览器打开并检查相对链接；Go 代码运行 `go test ./...`；涉及并发状态时再运行 `go test -race ./...`。
4. 用提交标题回答“这次变化为什么存在”。回答不清楚时，继续拆分改动。

合并前额外检查从 `main` 到当前分支的整体差异，并确认工作分支已同步到当前 `main`。若存在冲突，先理解两边意图；不要为了让 Git 停止报错而盲目选择一侧。

## 6. 首次建库基线

请先完成 [第 02 节 Git 工作流课](../lessons/0002-git-learning-workspace.html)。其中的命令卡解释了首次出现的每条 Git 命令、运行目录、影响范围、验证方式和可逆操作。

首次提交的推荐边界是“已有教学工作区的完整基线”：`AGENTS.md`、学习目标、资源、现有课程、参考资料、共享 assets、本规范、`.gitignore` 和 `.gitattributes`。推荐提交为：

```text
chore(repo): 建立学习工作区基线
```

首次建库只创建本机 `.git/` 元数据，不会联网或上传任何文件。添加远端前先检查上述跟踪边界，尤其是课程材料的来源、`.scratch/` 内容和 agent 配置；远端默认设为私有，除非已确认所有内容可公开。

## 7. 配置文件的约束

- `.gitignore` 只排除可以安全重建或绝不应共享的内容；新增忽略规则必须说明它保护什么，不能用它隐藏本应修复的问题。
- `.gitattributes` 将一般文本统一为 LF，以免 Windows 与 WSL2 的行尾变化制造无意义 diff；PowerShell/批处理脚本例外保留 CRLF。
- 不提交全局 Git 配置、凭据管理器文件、SSH 私钥、访问令牌或浏览器导出的 cookie。
- 不运行会改写或删除未提交改动的命令（例如 `reset --hard`、`clean -fd`），除非已经明确检查目标、确认改动可丢弃并获得授权。

## 8. 最小日常流程

1. 在 `main` 同步/检查状态后，创建一个命名清楚的工作分支。
2. 完成一个可验证的小目标；只暂存相关文件。
3. 运行相称验证，写原子提交。
4. 自审分支相对 `main` 的差异，以 fast-forward 合并，删除已完成分支。
5. 只在本地历史整洁且跟踪边界已检查后，才推送到远端。

速查版见 [Git 学习工作区速查表](../reference/git-learning-workspace.html)。
