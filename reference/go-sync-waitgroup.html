sync.WaitGroup 速查

WaitGroup 是一个完成计数器：协调“何时全部做完”，不负责“谁能同时读写状态”。

最常用模式

var wg sync.WaitGroup

for range workers {
	wg.Add(1) // 先登记一个即将开始的任务
	go func() {
		defer wg.Done() // 无论怎样返回，都在结束时注销任务
		doWork()
	}()
}

wg.Wait() // 计数归零前阻塞
操作计数器变化规则
wg.Add(n)加 n任务开始前登记；计数不能变为负数。
wg.Done()减 1等价于 wg.Add(-1)；通常放在 goroutine 起始处的 defer。
wg.Wait()不改变等待计数归零；通常由启动任务的 goroutine 调用。

它不做什么

问题WaitGroup？合适工具
所有 worker 是否结束？是WaitGroup
同一时刻只允许一个 worker 修改 hits？否sync.Mutex
把任务结果或取消信号传给另一个 goroutine？否channel / context
限制同时运行的 worker 数量？否有容量的 channel 或 semaphore

三条必须遵守的规则

  1. 先 Add，再启动 goroutine。当计数为零时，正数 Add 必须发生在 Wait 前；否则 Wait 可能已经返回。
  2. 每个 Add(1) 恰好匹配一次 Done()。漏掉 Done 会永久等待；多调用一次会使计数变负并 panic。
  3. 首次使用后不要复制 WaitGroup。传给函数时使用指针 *sync.WaitGroup；复用它等待另一批独立任务前，必须先让上一次的 Wait 返回。

与第一节计数器的关系

var c Counter        // c.mu 保护 c.hits
var wg sync.WaitGroup // wg 只追踪 worker 是否结束

wg.Add(1)
go func() {
	defer wg.Done()
	c.Add() // Add 内部仍须 Lock/Unlock
}()
wg.Wait()

Wait 返回意味着这个 goroutine 已执行完 Done 前的工作；但如果多个 worker 在运行期间同时写 hits，WaitGroup 不会阻止 race。Counter.mu 和 wg 各解决一个不同问题。

版本提示：wg.Go

Go 1.25 新增 wg.Go(func() { ... })，会启动 goroutine、增加计数，并在函数返回时自动减计数。你的 Go 1.26.5 支持它；但 6.5840 的最低环境是 Go 1.22，因此本课程主线仍使用兼容的 Add / defer Done 模式。传给 wg.Go 的函数不能 panic。
