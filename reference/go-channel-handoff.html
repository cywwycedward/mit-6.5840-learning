channel：交接任务，明确结束

用无缓冲 channel 把一个任务从发送者交给 worker；当发送者确定不会再发送时，由它关闭 channel，让接收循环自然退出。

本节的所有权规则

角色拥有的决定负责的动作
producer（生产者）还会不会产生新任务发送任务；确认结束后恰好调用一次 close(tasks)
worker（消费者）收到的当前任务从 tasks 接收并处理；不关闭它
tasks任务流，不是共享任务表传递值并让发送/接收在交接点同步

“由知道不会再发送的人关闭”是设计约定，不是编译器自动替你判定的规则。若有多个发送者，应先由它们协调出唯一的关闭者；多个 worker 都去关闭同一个任务 channel 是错误的所有权设计。

五个最小语法/API

写法逐项读取无缓冲时的行为
tasks := make(chan int)tasks 是变量；:= 声明它；make 创建可用的 channel；chan 表示 channel 类型；int 是其中允许传递的元素类型。没有容量参数，所以没有缓冲区；每次交接都要等待另一方。
tasks <- 7左边的 tasks 是目标 channel；箭头朝 channel 指，右边的 7 是要发送的 int。若没有接收者准备好，发送 goroutine 阻塞；有接收者配对后才能继续。
task := <-tasks右边的箭头从 channel 指向新变量 task；这次接收的结果赋给它。若还没有发送者，接收 goroutine 阻塞；有发送者配对后得到一个值。
close(tasks)close 是内置函数；圆括号内给出要关闭的 channel。声明“以后没有新任务”。之后发送会 panic；本节约定由唯一发送方调用一次。
for task := range tasks这是已讲过的 for/range；每轮取得一个收到的任务。等待任务；channel 关闭且已无可收任务时，循环结束，而不是产生一个假任务。

一次任务流的时序

producer worker -------- ------ 启动 worker goroutine 何时开始运行不由这里保证 tasks <- 8 ──等待配对──────────► 收到 8，处理一轮 tasks <- 13 ─等待配对──────────► 收到 13，处理一轮 close(tasks) 下一次取任务发现已关闭，循环结束 <-done ◄───────────────── done <- count，然后返回

无缓冲 channel 的每一条横线都是一次配对交接：发送方和接收方都到达该点，值才过去。Go 的内存模型规定，一次 send 会先于对应 receive 的完成，这正是它能同时传值和建立顺序的原因；但它不会自动保护其他 goroutine 同时修改的共享 map、slice 或 struct，那里仍要使用 Mutex 或明确所有权。

不要混用三种职责

你要回答的问题主要工具例子
谁把任务交给谁？何时没有更多任务？channel + closecoordinator 交给 worker 的任务流
谁能同时读写同一份可变状态？sync.Mutex任务表、计数器、内存 KV
已登记的 goroutine 是否全部结束？sync.WaitGroup主 goroutine 等待 worker

两个退出陷阱

  • 忘记关闭：任务已发完，但 worker 无法分辨“暂时没有任务”和“永远没有任务”；它会在 receive 上继续等待。
  • 关闭者不唯一：关闭后再发送或重复关闭都会 panic。先确定哪个 goroutine 掌握“发送结束”的事实，再让它独自关闭。
